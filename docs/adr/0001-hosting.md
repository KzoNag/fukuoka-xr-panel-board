# ADR 0001: ホスティングは「ローカルNodeサーバー + cloudflared クイックトンネル」

日付: 2026-09-18(イベント前日)

## 状況

参加者(現地スマホ + オンライン)は connpass 経由の一般参加者で、ログインなしで
トピック投稿・投票できる必要がある。準備時間は一晩。

## 検討した選択肢

1. **Claude Artifact + 共有DB(`db` / `room` / `artifact` capability)**
   - 最速で公開でき、サーバー不要。当初の第一候補
   - 却下理由: `db` を宣言した Artifact は組織内限定になり、公開リンクの
     未ログイン訪問者は読み書きともに不可(`db.d.ts` の ACCESS RULES を確認)。
     `room` も同組織の閲覧者しか接続しない。匿名の一般参加者が前提なので使えない
2. **Firebase RTDB / Supabase / Cloudflare Workers 等のマネージドバックエンド**
   - 安定した公開URLと真のリアルタイム同期が得られる
   - 却下理由: アカウント作成・プロジェクト作成・鍵の管理が必要で、前日の夜に
     人手の作業が増える。当日の障害時に切り分けが難しい
3. **ローカルNodeサーバー + cloudflared クイックトンネル**(採用)
   - 依存ゼロ・アカウント不要・ローカルで全機能を検証できる
   - 弱点: URLが起動ごとに変わる、ノートPCと会場Wi-Fiに依存する

## 決定

3 を採用。弱点への手当てとして

- ボードは `localhost` を見るのでトンネルが落ちても投影は止まらない
- `start.sh` がトンネル死活を監視して張り直し、参加者URLをサーバーへ再登録 →
  ボードのQRは自動で新URLに切り替わる。ただし**すでに旧URLで開いている参加者は追従できない**
  (相対パスで旧オリジンを叩き続ける)。参加者画面は接続断が続くと「QRを再読み込み」の案内を出し、
  進行役が口頭でも一声かける運用にした。固定URLが欲しければ named tunnel か選択肢2へ
- `--no-tunnel` で同一Wi-Fi限定のLANモードに逃げられる
- 状態は `data/data.json` に永続化し、再起動しても続きから

安定URLが欲しくなったら 2 へ移行する。データ層は `server.js` の API に閉じているので
フロントはそのまま流用できる。
